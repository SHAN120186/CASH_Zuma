# Подготовленное уменьшение трафика дневных отчётов

Ветка `codex/neon-report-aggregate-20261116`, база `4055788`. Кандидат для review, без автоматического изменения настроек бота. Развёртывание и включение дополнений выполняются отдельно.

## Решение

Вместо двух полных чтений всей истории проводок на каждый счёт отчёт один раз читает пять полей связанных со своими счетами проводок: source, target, kind, amount, date. Reader живёт только внутри прежней repeatable-read транзакции одного отчёта. Он повторно используется для начальных/конечных остатков, денег в пути и сверки выписки. Денежные guards записи не меняются.

Сохраняются исходные правила начального остатка в день открытия, обе стороны переводов, сторно, исторические даты и Python integer arithmetic. Ни межзапросного кэша, ни уменьшения частоты, ни shortcut по аудиту нет. Состав ответа, financial revision, авторизация и повторная проверка группы остаются прежними. После отдельного разрешённого восстановления настройки дополнения могут работать с прежней частотой 60 секунд.

## Доказательства

Синтетический fixture: старые чтения остатков 5, новые 1; сериализованный тестовый объём 661700 → 3771 байт. Это модель сравнения, не PostgreSQL wire measurement.


23 целевых теста (5 новых + 18 отчётов), 27 subtests; все 54 bot API теста; 4 прежних balance-теста; 484 frontend-теста и production build прошли. Тест конкурентной записи действительно инжектирует запись после начала snapshot и проверяет старую/новую revision. Проверены полное равенство JSON/revision, historical/incomplete/pending statements, transit positive/zero, открытия счетов, оба transfer legs, отсутствие общего кэша.

Остаются запросы самих операций дня, открытых заявок и банковских строк. Это не обещание нулевого трафика или конкретного процента снижения всего проекта.
