# ZUMA Cash Flow — сайт с входом и базой данных

**Версия 1.0 для пилотного запуска.** Это не статический HTML: интерфейс обращается к Python-серверу, операции и пользователи сохраняются в базе. Сайт НЕ размещён в интернете. Приложенный архив содержит исходный код, вашу FinModel и инструкции; публичного адреса он сам по себе не создаёт.

## 1. Самый простой запуск на Windows

1. Распакуйте ВЕСЬ архив, например в `C:\Zuma_CashFlow`. Не запускайте файлы прямо внутри ZIP.
2. Нужен установленный Python 3.12 или 3.13. При установке включите **Add Python to PATH**. На первом запуске нужен интернет для установки зависимостей; сама программа после установки не требует интернет для обычного учёта.
3. Дважды нажмите `START_WINDOWS.bat`. Он создаст `.venv`, установит библиотеки, подготовит SQLite и загрузит приложенную FinModel как отдельный снимок.
4. В консоли придумайте логин администратора (Enter предлагает `director`), введите имя и свой пароль минимум из 12 символов. Пароль вводится **без отображения символов** — это нормально. Повторите его. Общего пароля по умолчанию нет.
5. Браузер откроется на `http://127.0.0.1:8000`. Введите созданные логин и пароль.

Не закрывайте окно запуска: в нём работает сервер. Остановка — Ctrl+C. Повторный запуск сохраняет учёт и пользователей. **Не открывайте `app/static/index.html` двойным щелчком: ему нужен сервер.**

База находится в `data/cashflow.sqlite3`, оригиналы импортов — в `data/models`. Не удаляйте эту папку. Не размещайте SQLite на Google Drive, сетевой папке или в синхронизируемом каталоге; не запускайте несколько независимых копий учёта для разных сотрудников.

### Ручной запуск и Linux

```bash
python -m venv .venv
# Windows:
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe start.py
# Linux:
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python start.py
```

На Linux также есть `./start.sh`. Если 8000 занят, скопируйте `config.env.example` в `config.env` и задайте `PORT=8010`. Ошибки установки корпоративного прокси/сертификата решаются настройкой доверенного корпоративного сертификата и прокси, не отключением HTTPS-проверок.

## 2. Как зайти с телефона

Для теста запустите **START_FOR_PHONE.bat** вместо обычного запуска. Компьютер и телефон должны находиться в одной доверенной локальной сети. В консоли появится адрес вида `http://192.168.…:8000`; откройте именно его на телефоне. `127.0.0.1` на телефоне означает сам телефон, а не ваш компьютер. Windows Firewall может потребовать разрешение Python для частной сети. Не разрешайте доступ из публичной сети и не пробрасывайте порт роутера в интернет.

HTTP-режим LAN предназначен только для проверки интерфейса. Для реальных финансовых данных и удалённой работы нужны HTTPS и защищённая сеть/VPN либо сервер с доменом. Вариант PostgreSQL + HTTPS описан в `deploy/SERVER_RU.md`. Для ежедневной работы сервер должен быть постоянно включён.

## 3. Первые действия в системе

Откройте **Банк и касса** и добавьте каждый реальный счёт и кассу отдельно: валюта, подтверждённый остаток **на начало** выбранной даты. За эту дату затем внесите все фактические операции. По выписке сверяйте расчётный остаток с банком. В этой версии сверка ручная.

В **Пользователи** администратор создаёт сотрудников и роли. Для обычной работы заведите отдельного директора/финансиста, а технический администратор пусть используется для настройки. В **Лимиты** установите подтверждённые месячные бюджеты по статьям и валютам. Режим по умолчанию мягкий; при необходимости переключается на жёсткий с обязательной причиной.

Сотрудник создаёт заявку → руководитель согласует → заявка попадает в календарь → бухгалтер после реальной оплаты в банке подтверждает факт по документу. Платёж в интернет-банк не отправляется. Ожидаемое поступление создаётся в календаре и закрывается фактическим приходом.

## 4. Что уже работает

| Раздел | Реализовано |
|---|---|
| Вход и доступ | Пароли с солью и хешированием, серверные сессии, выход, смена пароля, отключение пользователя |
| Банк и касса | Раздельные остатки UZS/USD/EUR, начальная дата, контроль отрицательного остатка |
| Операции | Приход, расход, перевод между своими счетами одной валюты, CSV, сторно с причиной |
| Заявки | Черновик, отправка, утверждение/отклонение, перенос с повторным согласованием, полная оплата |
| Календарь | 7/30/90 дней, ожидаемые поступления, только утверждённые неоплаченные заявки, минимальный резерв |
| Лимиты | Статья × месяц × валюта, мягкий/жёсткий контроль, факт + резерв утверждённых заявок |
| FinModel | Отдельные версионные снимки, исходные адреса/формулы, план и факт, предупреждения исходника |
| Отчёт | Фактическое движение по статьям и месяцам из базы сайта; не подменяется данными модели |
| Контроль | Журнал действий, проверки на сервере, запрет повторного документа/оплаты, резервное копирование SQLite |

Суммы в базе — целые сотые доли валюты, расчёты не выполняются в `float`. Разные валюты НЕ складываются и НЕ конвертируются. Внутренние переводы не увеличивают внешний приход/расход. При оплате сумма переходит из резерва заявки в факт, а не учитывается дважды. После сторно исходная операция остаётся в базе, создаётся компенсация исходной датой; связанная заявка/ожидание открывается снова. Это бухгалтерское исправление учёта, не возврат денег из банка.

Просроченные ожидания в прогнозе условно отнесены на сегодня и помечены: пользователь должен уточнить дату. Не введённые обязательства не могут учитываться, поэтому отсутствие предупреждения не гарантирует отсутствие кассового разрыва.

## 5. Роли первой версии

| Роль | Возможности |
|---|---|
| Администратор | Все разделы, пользователи, лимиты, настройка и согласование; исключение самосогласования для запуска пилота отражено в интерфейсе |
| Директор | Обзор, отчёты, все заявки, согласование и перенос; без ввода факта и изменения лимитов |
| Финансист | Учёт, счета, лимиты, импорт модели, календарь, перенос, сторно; без утверждения |
| Бухгалтер | Счета, ввод факта, ожидаемые поступления, заявки, просмотр отчётов; без утверждения/лимитов/сторно |
| Сотрудник | Только свои заявки и собственный журнал; доступные названия счетов/статей для формы, без общих остатков и бюджетных сумм |

Руководитель не утверждает собственную заявку, кроме явно указанного администратора пилота. Для многоступенчатого маршрута «начальник → финконтролёр → директор», порогов сумм и строгого разделения администратора/согласующего нужна следующая доработка, это ещё не включено.

## 6. Ваша FinModel

В `source/FinModel_2026_Zuma_Pharm_v8.xlsx` находится копия прикреплённого файла. Оригинал не изменялся. Импорт считывает 35 названий листов и формирует 6 просмотров: P&L, Cash Flow из Statements, прямой Cash Flow, баланс, Opex и кредитный график. Диагностика анализирует выбранные листы, а не утверждает аудит каждой формулы во всех 35 листах.

**Модель нельзя целиком объявить планом.** В ней есть парные колонки план/факт и противоречивые периоды:

| Источник | Что сохранено без исправлений |
|---|---|
| `09_Statements`, строка 4 | Периоды P&L — 2026; строка 5 — план/факт |
| `09_Statements`, строка 26 | Периоды блока Cash Flow — 2025 |
| `09_CASH_Flow!C4:N4` | Периоды — 2023, хотя заголовок упоминает 2026 |
| `04_Opex!B6:M6` | Периоды — 2025 |
| `09_CASH_Flow_TEST` | В проверенных ячейках есть `#REF!` |
| `09_CASH_Flow!I54` и `09b_Balance!R8` | 1 350 593 723 и 1 457 280 281 соответственно: значения не согласованы между источниками |

Сайт показывает сохранённые Excel результаты; формулы не пересчитывает и ошибки не заменяет нулями. Результат формулы может быть устаревшим, если Excel не пересчитывали перед сохранением. Нулевой будущий факт не объявляется подтверждённым отсутствием операций.

Из-за этих ограничений модель НЕ заполняет автоматически остатки на сегодня, ежедневные платежи или бюджетные лимиты. Сначала финансист подтверждает период, единицу измерения, статью и срок платежа. Сам снимок остаётся доступным для сравнения. При изменении структуры книги необходимо обновить адаптер `app/model_import.py` и тесты.

## 7. Google Drive

В конфигурации предусмотрен файл `1XCZbSDWBLjf-X5lqvBaLQhvb3R0eRSRr`. **Доступ ChatGPT к Диску не передаётся этому сайту. Живая синхронизация здесь не настроена и не протестирована с вашим аккаунтом.**

Для первого запуска ничего подключать не нужно — копия Excel уже включена. Новую копию можно импортировать кнопкой **FinModel → Импорт XLSX**. Импорт создаёт версию; идентичный файл не дублируется (SHA-256), операции сайта не меняются.

Для самостоятельного чтения Drive сервером:

1. В своём Google Cloud проекте включите Google Drive API, создайте отдельный сервисный аккаунт. Организация должна разрешать такой способ доступа. Делегирование полномочий всего домена НЕ нужно.
2. Поделитесь **только нужным файлом** с адресом сервисного аккаунта как с читателем; не включайте «доступ всем по ссылке».
3. Ключ храните только на своём сервере вне репозитория/публичного каталога, ограничьте права чтения. Не отправляйте ключ или пароль в чат. При запрете ключей организацией используйте её утверждённый способ авторизации; эта версия готова только к сервисному аккаунту с локальным ключом.
4. Установите `requirements-drive.txt`, скопируйте `config.env.example` в `config.env` и задайте:

```ini
GOOGLE_DRIVE_FILE_ID=1XCZbSDWBLjf-X5lqvBaLQhvb3R0eRSRr
GOOGLE_APPLICATION_CREDENTIALS=C:/Zuma_CashFlow/secrets/drive.json
```

После перезапуска кнопка «Обновить из Drive» выполняет чтение по запросу. Предусмотрены XLSX и экспорт Google Sheets. Права `drive.readonly` ограничивают операции чтением, а доступ к конкретным файлам ограничивается тем, какие файлы вы открыли сервисному аккаунту. Фоновое расписание намеренно не включено; команда для отдельного ручного запуска: `python manage.py sync-drive`.

## 8. Резервные копии и пароли

`BACKUP_WINDOWS.bat` создаёт архив SQLite и оригиналов импортированных моделей в `backups`. Копия содержит финансовые сведения и хеши паролей: храните её шифрованно и с ограниченным доступом, проверяйте восстановление. Резервная копия на том же диске не защищает от поломки этого диска.

Для восстановления SQLite остановите сайт, сохраните текущую папку `data` целиком, затем в отдельной чистой папке `data` восстановите `cashflow.sqlite3` и `models` из проверенной копии. Не заменяйте SQLite при работающем сервере и не оставляйте старые `-wal`/`-shm` рядом с восстановленным файлом. После проверки входа и сумм возобновите работу.

Забытый пароль сбрасывается на сервере, например:

```bat
.venv\Scripts\python.exe manage.py reset-password director
```

Введите новый пароль в консоли. Все старые сессии этого пользователя будут отозваны. Безопасного сброса по электронной почте/MFA/SSO в этой версии нет.

## 9. Границы готовности

Локальная серверная логика, SQLite, импорт предоставленного Excel и API проверены автоматическими тестами. Интерфейс отрисован в Chromium на 1440 и 390 px, с обращениями к реальному API через локальный тестовый адаптер. Полный браузерный сетевой проход HTTPS, Windows BAT, Docker, PostgreSQL и живая авторизация Google не проверены в среде сборки — их проверяет администратор при размещении. Это **не независимый аудит безопасности и не промышленная приёмка**.

Не реализованы: банковские API/загрузка выписок конкретного формата/автосверка, отправка денег в банк, частичная оплата заявки, вложения счетов, мультикомпания, валютная конвертация, закрытие периода, многоступенчатое согласование, редактирование/отмена ожидаемого поступления отдельной командой, автоматическое распределение месячного бюджета по дням. Список операций и заявок ограничен последними 500 записями; CSV выводит все операции. Аудит в UI не удаляется, но администратор самой БД технически способен его изменить; криптографической неизменяемости нет.

В первой версии схема создаётся при запуске (`create_all`); система миграций ещё не добавлена. Переход SQLite → PostgreSQL не переносит существующий учёт автоматически. До внедрения проверьте восстановление резервной копии, разграничение доступа, лимиты, сверку остатков, журналирование, внешнюю безопасность и актуальность зависимостей. После обновления библиотек повторите тесты.

**Архив конфиденциальный: внутри финансовая модель компании. Не публикуйте архив, Docker-образ, `source`, `data`, `.env` или ключи в открытом репозитории.**
