В Zuma найдены все шесть ограниченных статей таблицы. В UZGERMED:

на них не переносится. Одинаковые подтверждённые наименования получают одинаковое
правило при создании или миграции в любой компании. Имена и прежние политики
согласования в ходе проверки не изменялись.

## Прямое согласование на изолированных данных

Расширен `tests/test_director_limits.py`. Для **каждой** из двух фирм создаются
отдельный счёт и независимые бухгалтер, финансовый директор и директор.
Заявки проходят штатные документы, отправку, проверку бухгалтера и финансового
директора, затем вызывается настоящий HTTP endpoint окончательного согласования.

| Проверка в каждой фирме | Результат |
|---|---|
| Основные средства: 99 999 999,99 UZS | 200, approved |
| Основные средства: 100 000 000,00 UZS | 200, approved |
| Основные средства: 100 000 000,01 UZS | 409, остаётся pending |
| Каждая из пяти статей с нулём: 0,01 UZS | 409, остаётся pending |
| Статья «без лимит»: 100 000 000,01 UZS | 200, approved |
| Попытка передать сумму/статью/снять лимит в approve payload | 422, без изменения заявки |

Это **18** обычных финальных решений (12 отказов и 6 разрешений) и **6** попыток
подмены полей, повторённых на каждой СУБД. При отказе проверены неизменность
версии, суммы, статьи, статуса и отсутствие подписавшего директора; Ledger
остаётся пустым. Интерфейс также не предлагает approve для превышенной суммы.

Итоговый набор: **11 тестов SQLite и 11 тестов PostgreSQL 17 успешны**.
Существующие проверки дополнительно покрывают финальный этап без директора,
skip, текущий лимит старой pending-заявки, ноль/null, отдельные валюты, комиссию
по своей статье и общую сумму при совпадении статьи, права и изоляцию компаний.
Временный PostgreSQL остановлен после прогона.

Независимое чтение кода не выявило обхода: сервер берёт сумму и статью из БД,
валюту из реального счёта и проверяет текущий лимит до записи согласования
в той же защищённой транзакции. Директор не может изменить верхний лимит сам.

## Общий CI

У опубликованного коммита run `42091814948` завершился ошибкой на совместном
запуске двух модулей истории/производительности. Первый модуль вызывает очистку
общей временной папки; второй после этого теряет тестовую базу или файл блокировки.
Это ошибка последовательности тестов, а не отказ проверки лимитов. Запуски
этих двух модулей разделены на отдельные процессы в обоих jobs CI.
Раздельные локальные прогоны также успешны на обеих СУБД: по 1 тесту
производительности и по 6 тестов истории. В проверке действий 1/10/50 активных
заявок сохраняется по 10 SQL для finance/accountant/cashier.
Полный новый облачный прогон не подменяется результатами целевых локальных тестов.

Полный GitHub CI проверочного коммита `ffee38e` впоследствии завершился
успешно: [run 42096501083](https://github.com/SHAN120186/CASH_Zuma/actions/runs/42096501083).
По разрешению владельца проверки передаются в main через PR #102.
Приложение идентично опубликованной 2.35.9, повторный Render deploy не требуется.
