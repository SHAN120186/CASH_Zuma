# ZUMA · Мини-ERP Казначейство

## Запуск на этом компьютере

Откройте `START_LOCAL.bat`. Он запускает выделенный PostgreSQL, API и worker резервного копирования/рассылки. Интерфейс: http://127.0.0.1:8001. Логин и пароль существующего пользователя сохранены. Порт 8000 может обслуживать старую отдельную копию с рабочего стола; её данные больше не являются данными этой платформы.

Для второго ноутбука в той же доверенной Wi‑Fi/LAN сети используйте `START_ON_NETWORK.bat`. В консоли будет адрес вида `http://192.168.x.x:8001`; второй пользователь открывает его в браузере и входит под своей учётной записью. Такой запуск не публикует систему в интернет. Если Windows спросит про брандмауэр, разрешайте Python только для частной сети. Не используйте этот режим в общественном Wi‑Fi и не открывайте порт на роутере.

`ZUMA_DEMO_COPY.html` — автономная просмотрная HTML-копия с демонстрационными суммами. Её можно скопировать на другой ноутбук и открыть в браузере без установки и без доступа к финансовым данным.

PostgreSQL 17 слушает только 127.0.0.1:55432. Каталог кластера — `%LOCALAPPDATA%/ZumaTreasury/postgres17`, вне OneDrive. Параметры подключения и JWT находятся в исключённом из Git `config.local.env`. Файл не публиковать. Учётная запись БД локального стенда создана initdb; перед публичным развёртыванием используйте отдельную роль приложения без superuser.

Исходная SQLite сохранена в `data/cashflow.sqlite3`, её согласованная резервная копия — `backups/before-postgres-20260917-072043.sqlite3`. Рабочие записи теперь поступают в PostgreSQL. Переключение обратно на SQLite после новых операций потеряет видимость этих операций: нужен отдельный обратный перенос, а не смена настройки.

## Реализованные требования

| Требование | Реализация |
|---|---|
| SPA | Vue 3, Vite; исходники `frontend/`, готовая сборка `app/static/erp/` |
| REST API | Python/FastAPI, GET/POST/PUT/DELETE, серверные проверки прав |
| PostgreSQL 14+ | Рабочая локальная PostgreSQL 17; SQLite оставлена для совместимости и тестов |
| Пользователи и роли | `users`, `roles`, связь `role_id`; старое поле `role` синхронизируется для совместимости |
| Статьи | Доход/расход + операционная/инвестиционная/финансовая деятельность; создание и редактирование администратором |
| Транзакции | Существующий `ledger`: дата, тип, сумма, статья, контрагент, описание (`note`), документ (`reference`), связь со счётом и заявкой |
| Документы | Таблица `documents`, защищённый URL `/api/documents/{id}`; PDF/PNG/JPEG до 5 МБ; содержимое включено в резервную копию БД |
| Бюджеты | Лимит × статья × месяц × валюта; мягкий/жёсткий контроль; факт + резерв утверждённых заявок |
| Импорт | CSV UTF-8 и XLSX, до 1000 операций/5 МБ, первый лист XLSX; предпросмотр и отдельное подтверждение; повторная валидация при записи, атомарный откат |
| Google Sheets | Серверный экспорт Google Sheets в XLSX через Drive API; тот же предпросмотр/подтверждение реестра |
| Отчёты | Cash Flow по статьям и месяцам; XLSX/PDF, CSV реестра; внутренние переводы и сторно не увеличивают обороты |
| Авторизация | Подписанные HS256 JWT, 60 минут, проверка issuer/audience/expiry; серверный отзыв сессий; HttpOnly cookie + CSRF либо Bearer API |
| Пароли | bcrypt cost 12 с SHA-256 prehash (поддержка длинных/Unicode паролей без обрезки 72 байт); старый PBKDF2 обновляется после успешного входа |
| Аудит | Изменения с подробностями и API-действия с путём/статусом; без паролей, токенов и тел запросов |
| Рассылка | Ежедневные XLSX/PDF, валюта и получатель, час Ташкента; отдельный worker, только включённые расписания |
| Бэкапы | pg_dump custom ежедневно при работающем worker; проверка pg_restore --list; ручной `python worker.py --backup` |

Старый интерфейс доступен на `/legacy`, в частности для просмотра исторической FinModel. Это переходный экран; основной интерфейс работает на Vue. FinModel не превращается автоматически в реальные операции.

## Права

| Роль | Доступ |
|---|---|
| Администратор | Все модули, справочники, пользователи, аудит, расписания |
| Директор | Просмотр финансов, аналитика, экспорт; без согласования и записи |
| Казначей (`finance`) | Операции, счета, импорт, бюджеты, календарь, заявки и согласование чужих заявок |
| Бухгалтер | Только реестр и скачивание прикреплённых документов; без записи, бюджета и экспорта отчётов |
| Аудитор | Просмотр финансов, заявок, отчётов и журнала; без изменения данных и управления пользователями |

Роль `employee` («Инициатор») видит и редактирует только свои неутверждённые заявки. Автор и последний редактор не могут согласовать заявку, включая администратора; нужен отдельный согласующий. Возврат, отмена и перенос снимают утверждение и резерв. Тип статьи — классификация, не запрет возвратов противоположного направления по той же статье. При переносе старых статей без типа они помечены расходными, кроме стандартных статей поступлений; администратор должен проверить классификацию своих дополнительных статей.

С 19 сентября 2026 заявки имеют `version`. PUT заявки и POST решения передают текущую версию; факт оплаты передаёт `request_version`. Устаревшая версия возвращает 409; отсутствие версии для решения/оплаты — 428. После конфликта обновите список и повторно проверьте документ. При редактировании версия — обязательное поле. Существующие финансовые записи сохраняются при добавлении колонок.

Календарь позволяет сравнивать утверждённые оплаты и все заявки с учётом согласования; оба сценария включают ожидаемые поступления, которые ещё не подтверждены банком. Черновики, возвраты, отказы и отмены не входят в прогноз. Входящий и исходящий остатки показаны по каждому дню; риск проверяется также по отдельным счетам.

## Формат импорта

Скачайте шаблон на странице «Импорт данных». Столбцы:

`date;kind;account_id;to_account_id;category_id;amount;counterparty;reference;note`

- date: ГГГГ-ММ-ДД; kind: in/out/transfer; amount: положительная сумма с точкой, до двух десятичных знаков.
- ID счетов и статей показаны на странице импорта. Валюта определяется счётом.
- Для перевода to_account_id обязателен, category_id пустой. Конвертация валют не выполняется.
- Номер reference уникален в рамках счёта. Для расхода без заявки note содержит основание от 10 символов.
- Формулы XLSX отвергаются; вставьте значения. Ошибки покажут номера строк. Пакет с ошибками не подтверждается.

## Подключение Google Sheets

В `config.local.env` задайте `GOOGLE_SHEETS_TRANSACTIONS_ID` и `GOOGLE_APPLICATION_CREDENTIALS` (путь к JSON-ключу сервисного аккаунта). В Google Cloud включите Drive API, предоставьте сервисному аккаунту чтение конкретной таблицы. Первый лист должен соответствовать шаблону операций. Установите `requirements-drive.txt`, перезапустите сервер. Ключ не помещается в браузер и не передаётся в чат. `GOOGLE_DRIVE_FILE_ID` отдельно относится к исторической FinModel.

Живое подключение не активировано: ссылка/ID и серверный ключ пока не предоставлены.

## Рассылка

На сервере задайте SMTP_HOST, SMTP_PORT, SMTP_FROM, SMTP_USER, SMTP_PASSWORD, SMTP_TLS_MODE (`starttls` или `ssl`), затем перезапустите API и worker. TLS и проверка сертификата обязательны. В разделе «Рассылка» администратор задаёт адрес, валюту, час и явно включает расписание.

Отправляется текущий год. Worker проверяет расписания раз в минуту. Одна попытка на расписание в день; при неопределённом результате или ошибке автоматический повтор в тот же день не выполняется, чтобы не дублировать финансовые письма. Статус ошибки виден в интерфейсе. Если администратор-создатель отключён или лишён роли, расписание отключается. Реальные письма в ходе разработки не отправлялись.

## Бэкапы и восстановление

Бэкапы находятся в `backups/` (в Docker — отдельный volume `backup_data`). Копии не удаляются автоматически. Это локальные копии; хранение вне компьютера/сервера нужно настроить отдельно. Снимки исходных Excel в `data/models` и конфигурацию храните отдельно от pg_dump: они не являются таблицами БД. При выключенном компьютере/worker расписание не выполняется.

Для восстановления остановите API/worker, создайте новую пустую БД, используйте `pg_restore --no-owner --exit-on-error --dbname <новая_БД> <копия.dump>`, проверьте роли, записи, остатки и документы, затем переключите DATABASE_URL. Пароли БД передавайте через защищённую среду/pgpass, не командную строку. Проверка восстановления на отдельной временной базе: `python tests/verify_backup.py`.

## Разработка и проверки

### Подсказки при входе

Форма запоминает три последних уникальных логина после успешной авторизации. Они показываются под полем и в его выпадающем списке; при вводе подсказки фильтруются, при выборе фокус переходит к паролю. Новый вход поднимает логин наверх. История хранится только в текущем браузере для текущего адреса сайта: другой ноутбук, браузер или переход с localhost на сетевой IP имеют отдельную историю. Неудачные попытки её не пополняют. Если браузер запрещает локальное хранилище, вход продолжает работать, а история остаётся только до перезагрузки страницы.

Поля поддерживают штатное автозаполнение логина и пароля. В поддерживаемом защищённом контексте после успешного входа также запрашивается сохранение через менеджер паролей браузера. Сайт не записывает пароль в localStorage или историю логинов. Сохранение/подстановка зависят от браузера и его настроек; при первом входе может понадобиться подтверждение «Сохранить». На сетевом HTTP-адресе программный Credential Management API недоступен; встроенный браузер приложения также может не поддерживать менеджер паролей. В таком случае используйте основной браузер с включённым сохранением паролей. Принудительно включить менеджер со стороны сайта нельзя.

Проверка этой логики: `cd frontend`, затем `node --test tests/loginPreferences.test.js` (7 тестов).

### Команды разработки

Backend: `.venv-local/Scripts/python.exe -m pip install -r requirements.txt`. Дополнительные библиотеки тестов — `httpx==0.28.1`. Frontend: из `frontend` выполните `pnpm install --frozen-lockfile` и `pnpm run build` (Node 24, pnpm 11.19). Сборка не загружает JavaScript с CDN.

- `python tests/test_site.py` — 48 тестов на отдельной SQLite.
- `python tests/run_postgres.py` — те же 48 тестов на одноразовой PostgreSQL-базе. Имя обязательно начинается `zuma_test_`, рабочая БД не очищается.
- `python tests/verify_backup.py` — создание и восстановление настоящего pg_dump в одноразовой базе.

Серверное размещение: `compose.yaml`, PostgreSQL 17, Caddy HTTPS, отдельный worker. Заполните `.env` по `.env.server.example`; для Google используйте дополнительный `compose.drive.yaml`. Docker не установлен в этой среде, поэтому контейнерный запуск и внешний HTTPS здесь не проверены.

Это проверенная локальная версия, не независимый аудит безопасности и не нагрузочная приёмка. Для промышленной эксплуатации нужны внешнее хранилище бэкапов, мониторинг, ограниченная роль PostgreSQL, домен/HTTPS и проверка SMTP/Google с реальными серверными настройками.
