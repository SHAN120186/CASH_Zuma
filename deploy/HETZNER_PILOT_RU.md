# Изолированный тест Cash Zuma на Hetzner

Это подготовленный сценарий, а не подтверждение переноса. Сервер и платные ресурсы
этими файлами не создаются. Фактические наличие тарифа, стоимость, срок теста и
готовность аккаунта проверяются в Hetzner Console до заказа. Рабочий Render остаётся
основной системой до принятия результатов владельцем.

## Границы теста

- Отдельный x86-64 VPS с Ubuntu 24.04, Docker Engine и Compose v2. Ориентир для
  приложения вместе с PostgreSQL и генерацией PDF — 8 ГБ RAM; достаточность проверяет тест.
- Один и тот же исходный commit, что работает на Render. Инфраструктурные файлы
  могут находиться в более позднем коммите, но приложение для сравнения фиксируется отдельно.
- Отдельная копия PostgreSQL и всего `DATA_DIR`, включая модели. Копирование рабочих
  данных на новый сервер выполняется только в согласованном владельцем объёме.
- `compose.hetzner-pilot.yaml` запускается **самостоятельно**, без основного
  `compose.yaml`: проект `cashzuma-pilot`, собственные тома, локальная БД `cashzuma_pilot`.
- PostgreSQL 18 совместим с исходной БД версии 18. Для официального образа 18
  том подключён к `/var/lib/postgresql`, а не к пути образа 17 из основного шаблона.
- Приложение слушает только `127.0.0.1:18000` на VPS. Интернет-доступ к 8000,
  18000 и 5432 не открывается. Доступ к тесту — через SSH-туннель.
- Контейнеры находятся во внутренней сети, без исходящих интеграций. Worker,
  SMTP, рабочие ключи бота и Google не подключены. Внешняя отправка отчётов,
  Drive-синхронизация и Telegram не являются частью этого пилота.

Второй web нельзя подключать к рабочей Neon даже «для чтения»: startup запускает
инициализацию схемы и служебную очистку, вход и авторизованные GET пишут аудит.
Рабочие `DATABASE_URL`, JWT, cookie или токены в пилот не переносятся. Существующие
пользователи и их хеши паролей могут присутствовать только в разрешённой изолированной
копии базы; сеансы копии не дают доступ к рабочему сайту из-за отдельного JWT.

## Подготовка до запуска web

Пример каталогов VPS:

```text
/opt/cash-zuma-pilot/          # checkout исходников
/opt/cash-zuma-pilot-private/  # режим 0700: env, dump, архив DATA_DIR, доказательства
```

Приватный каталог находится вне build context и Git checkout. Файлы секретов и
копий имеют режим 0600. В нём создать `pilot.env` с двумя **разными новыми**
случайными секретами по 32 байта в hex-формате:

```text
PILOT_DB_PASSWORD=<64 случайных шестнадцатеричных символа>
PILOT_JWT_SECRET=<другие 64 случайных шестнадцатеричных символа>
PILOT_RESTORE_CONFIRMED=no
```

Каждый секрет можно сгенерировать `openssl rand -hex 32`. Не вставлять значения в
команды, переписку или журналы. Compose требует заполнения секретов; entrypoint
отклоняет неверную длину, текстовые placeholders, нулевые значения и одинаковые
DB/JWT-секреты. Переменная `DATABASE_URL` хоста не используется: URL БД формируется
в Compose с постоянными локальными host/database.

Из корня checkout:

```bash
docker compose --env-file /opt/cash-zuma-pilot-private/pilot.env -f deploy/compose.hetzner-pilot.yaml config --quiet
docker compose --env-file /opt/cash-zuma-pilot-private/pilot.env -f deploy/compose.hetzner-pilot.yaml build web
docker compose --env-file /opt/cash-zuma-pilot-private/pilot.env -f deploy/compose.hetzner-pilot.yaml up -d db
```

`config --quiet` проверяет конфигурацию, не печатая раскрытые секреты. Полный
`docker compose config` с рабочими значениями в общий лог не записывать.

Создать согласованную копию PostgreSQL клиентом `pg_dump` версии 18 или новее,
сохранить custom-format архив и проверить `pg_restore --list`. Скопировать архив
и весь `DATA_DIR` через SSH, сверить контрольные суммы/манифест файлов. Хранить
копии только в приватном каталоге. Восстановление выполняется только в пустую
изолированную БД пилота:

```bash
docker compose --env-file /opt/cash-zuma-pilot-private/pilot.env -f deploy/compose.hetzner-pilot.yaml exec -T db pg_restore --exit-on-error --single-transaction --no-owner --no-privileges -U pilot -d cashzuma_pilot < /opt/cash-zuma-pilot-private/restore.dump
```

При ошибке расширения или несовместимого объекта остановиться и разобрать
расхождение; не пропускать ошибки восстановления. `--single-transaction`
предотвращает частичное восстановление этой команды.

Далее заполнить том `pilot_data` полной проверенной копией `DATA_DIR`, сохранив
относительные пути и назначив владельца UID/GID `10001:10001`. Для разового
копирования разрешён служебный контейнер образа web с переопределённым entrypoint
и без запуска приложения. Архив сначала проверить на абсолютные пути, `..` и
неожиданные ссылки. Сверить файлы после копирования; не выполнять `manage.py
create-admin` или сброс рабочих паролей для восстановленной копии.

До первого запуска web сравнить основные количества записей, суммы и остатки
исходной согласованной копии и восстановленной БД. Затем заменить в приватном
`pilot.env` только маркер на `PILOT_RESTORE_CONFIRMED=isolated-copy-verified`:

```bash
docker compose --env-file /opt/cash-zuma-pilot-private/pilot.env -f deploy/compose.hetzner-pilot.yaml up -d web
docker compose --env-file /opt/cash-zuma-pilot-private/pilot.env -f deploy/compose.hetzner-pilot.yaml ps
curl --fail http://127.0.0.1:18000/health
curl --fail http://127.0.0.1:18000/ready
curl --fail http://127.0.0.1:18000/version.json
```

Entrypoint web требует маркер восстановления. Автоматического создания
администратора нет. Контрольный вход выполняется в копию существующим разрешённым
аккаунтом; изменения в пилоте остаются в его изолированных томах.

## Доступ с компьютера проверяющего

```bash
ssh -N -L 127.0.0.1:18000:127.0.0.1:18000 <ssh-user>@<pilot-ip>
```

После проверки ключа сервера открыть `http://127.0.0.1:18000`. SSH-туннель
шифрует сетевой участок; HTTP и cookie без Secure ограничены loopback на двух
концах туннеля. Не менять bind на `0.0.0.0`, не открывать порт публично и не
использовать этот HTTP-режим для постоянной эксплуатации. Публичный HTTPS с
собственным доменом и reverse proxy — отдельный этап после пилота.

## Проверка результата

1. Зафиксировать commit приложения, release, Docker image IDs, ресурсы VPS,
   PostgreSQL `server_version`, дату согласованной копии и размер данных.
2. Проверить обе компании, границы ролей, обзор, заявки и открытие карточки,
   скачивание существующего вложения, Cash Flow/P&L/баланс и модели. Фактические
   рабочие платежи при тесте не выполнять.
3. Сравнить одинаковые списки и фильтры: bootstrap, 10/50 заявок, карточку и файл.
   Отдельно измерить API до первого байта/полного ответа и UI до кликабельных строк.
   Холодный первый запрос отделить от повторных; для p95 нужен достаточный набор,
   а не 2–3 измерения. Проверить 1 и 5 одновременных пользователей.
4. Замер с компьютера через SSH включает накладные расходы туннеля. Сравнение с
   публичным HTTPS Render пометить этим ограничением; для окончательного решения
   нужен одинаковый клиент и сопоставимый транспорт HTTPS.
5. Не называть пилот успешным только по `/health`: он не читает БД. Проверить
   `/ready`, реальные данные и восстановление, затем записать результат и ограничения.

Рабочий DNS и Render в этом сценарии не переключаются. По окончании остановить
пилотные контейнеры, сохранив тома; `down -v` не применять. Выключенный VPS и
выделенный IPv4 продолжают тарифицироваться до удаления — дальнейшее содержание
или удаление ресурсов согласуется с владельцем отдельно.

[переменные Compose](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/),
[биллинг Hetzner](https://docs.hetzner.com/cloud/billing/faq/).
