# Срочная защита заявок и оплат — PR 2

Ветка `claude/payment-safeguards` от `main`, без редизайна интерфейса. Требования — из `Claude_followup_after_access_audit.txt`. Полная модель ролей и компаний (PR 3) не начиналась.

## Что изменено

| Требование | Как сделано |
|---|---|
| Автор, последний редактор, финансист и директор-согласующий не оплачивают заявку | Сервер отклоняет оплату с кодом 403, если плательщик — один из участников заявки. Проверка выполняется до чтения версии и суммы. |
| Отдельные права `pay_bank` и `pay_cash`; `write` не оплачивает | Банковскую заявку оплачивает расчётный бухгалтер (`pay_bank`), кассовую — кассир (`pay_cash`). У кассира убрано общее право `write`: он использовал его только для оплаты. Канал определяется типом счёта заявки. После первых операций, заявок или поступлений тип счёта менять нельзя. |
| Сумма, валюта, статья, счёт и получатель — из заявки | Любое расхождение возвращает 409, в том числе поля `to_account_id` и `receipt_id`. Получатель в операции берётся из заявки. Дата оплаты — не раньше утверждения и не позже сегодняшнего дня. |
| Нехватку денег или бюджета нельзя обойти комментарием | Комментарий плательщика в проверке не участвует. Сервер отвечает 409 с подсказкой, а новое действие «Вернуть финансовому директору» (`return_finance`) переводит заявку на этап финансиста с обязательной причиной. Деньги проверяются на дату оплаты, на сегодня и на срок самой заявки, поэтому ни дата задним числом, ни ранняя оплата не забирают резерв других заявок. Допускается только мягкое превышение статьи за месяц, которое согласующие приняли при утверждении, если заявка сама утверждалась на месяц оплаты. Если срок заявки в другом месяце, сообщение просит перенести срок на месяц оплаты и утвердить заявку заново. При жёстком лимите оно просит сначала пересмотреть бюджет. |
| Резерв защищён и от других расходов | Расход без заявки и перевод со счёта проверяются на свою дату и на сегодня. Они не уносят деньги, зарезервированные под утверждённые заявки, срок которых наступил. Раньше дата задним числом обходила эту проверку, а перевод не проверялся совсем. |
| Атомарность и защита от двойной оплаты | Всё прежнее сохранено: общая блокировка записи, версия заявки, статус `approved → paid` в одной транзакции, уникальный `ledger.request_id`. |
| `reject` убран | API отвечает 422 с подсказкой вернуть заявку на доработку. В интерфейсе нет кнопки «Отклонить». Прежние отклонённые заявки открываются и фильтруются, но их нельзя править, отменять, отправлять, утверждать или оплачивать. |
| Директор для каждой заявки | Утверждение финансистом всегда оставляет заявку на этапе директора. Сохранённые пороги не действуют. Настройка порога отвечает 409, а страница «Согласование» описывает порядок. Заявки, которые прежний порог пропустил без директора, к оплате не допускаются: их возвращают финансовому директору, после чего их утверждает директор. |

## Миграция

Две новые колонки в `payment_requests`, обе допускают NULL. Они добавляются автоматически при старте, в `initialize()`, повторный запуск безопасен.

| Колонка | Тип | Значение |
|---|---|---|
| `approved_at` | `TIMESTAMP` | время окончательного утверждения |
| `approved_overrun` | `BIGINT` | мягкое превышение бюджета, принятое при утверждении, в тийинах |

Существующие строки не меняются. `tests/verify_company_migration.py` учитывает новые колонки.

Для уже утверждённых неоплаченных заявок время утверждения не записано, поэтому у них нижняя граница даты оплаты — дата создания заявки. Мягкое превышение, принятое до этого PR, не записано. Если бюджет такой заявки уже превышен, оплата остановится с подсказкой вернуть её финансовому директору. Так же остановится оплата заявки, утверждённой прежним порогом без директора.

Перед выкладкой полезно проверить, есть ли в рабочей базе такие заявки:

```sql
SELECT id, status, finance_approved_by, approved_by FROM payment_requests
WHERE status = 'approved' AND (approved_by IS NULL OR finance_approved_by IS NULL OR approved_by = finance_approved_by);
```

## Вопросы владельцу

- **Администратор на этапе директора.** Он по-прежнему может утвердить заявку на этапе директора, как и до PR, а два разных администратора проходят оба этапа. Если по Q03 нужен именно пользователь с ролью «Директор», это меняется одной проверкой. Но тогда компания без такого пользователя не сможет утверждать заявки, поэтому сначала нужно назначение по Q15.
- **Прежние мягкие превышения.** Мягкое превышение, принятое до выпуска, не сохранено. Заявку, утверждённую раньше в месяце, где мягкий лимит уже превышен, после выкладки один раз утверждают заново.

## Что остаётся за рамками PR

- **Расход без заявки:** роли с `write` (администратор, директор, финансист, оператор) по-прежнему могут записать фактический расход без заявки — вручную или импортом. Это не оплата заявки, её ограничение относится к модели ролей (PR 3).
- **Сторно:** операция возвращает заявку в статус «утверждена» с прежними согласующими. Повторная оплата снова проходит все проверки этого PR.
